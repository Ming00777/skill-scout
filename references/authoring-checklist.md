# 自建 Skill 清单

找不到合适的现成 Skill 时，帮用户建一个。这份清单是实操要点，不是教程。

## 最小可用骨架

```
skill-name/
  SKILL.md        # 必需，其他全是可选
  scripts/        # 需要确定性逻辑时才加（如解析、检索、批量处理）
  references/     # 内容太长、按需加载时才加
```

一个 Skill 可以只有一个 SKILL.md。**不要一上来就建一堆目录**。

## frontmatter：`description` 决定成败

```yaml
---
name: my-skill
description: 一句话说明它干什么。加上「当用户说 X、想做 Y、遇到 Z 时使用」这类触发条件。
---
```

两个铁律：

1. **description 是唯一的匹配依据。** Agent 启动时只读各 Skill 的 name + description，描述写得含糊，它就永远不会被触发——写得再好的正文也没用。
2. **必须写触发条件，不能只写功能。** 写"处理表格"没用；要写"当用户要把 CSV 转成带样式的 Excel、或抱怨表格太丑时使用"。要包含用户可能说出口的原话。

反例：`description: 一个有用的前端工具` → 永远不会被触发。
正例：`description: 审计并重写前端 UI，去掉 AI 味设计（紫渐变、Inter、默认 shadcn）。当用户说"UI 好丑"、"这看起来像 AI 生成的"、"去 AI 味"时使用。`

## 正文结构

按这个顺序，缺哪块补哪块：

- **When to Use** —— 什么情况触发
- **When NOT to Use** —— 什么情况别用（避免和其他 Skill 抢触发）
- **Instructions** —— 分步说明，步骤要具体可执行
- **Examples** —— 输入输出示例（有就加，效果提升明显）

## 常见坑

| 坑 | 后果 |
|---|---|
| description 里没写触发条件 | Agent 匹配不到，Skill 等于没装 |
| SKILL.md 写得过长（>500 行） | 挤占上下文，应该拆到 `references/` 按需加载 |
| 把所有细节堆在主文件 | 同上，主文件只留主干流程 |
| 靠 LLM 自由发挥做确定性工作 | 结果不稳定，应该写成 `scripts/` 里的脚本 |
| 一次塞太多能力 | 触发混乱，一个 Skill 干一件事 |

## 什么时候该写脚本而不是靠提示词

判断标准：**这件事有没有唯一正确答案？**

- 有（解析 frontmatter、统计文件类型、扫描目录）→ 写成脚本，确定性执行
- 没有（判断用户需求、生成文案、设计方案）→ 用提示词交给 LLM

## 现成范例

本仓库自身就是个可参考的骨架：主流程在 `SKILL.md`，确定性逻辑在 `scripts/`（探测、检索、扫描、分析），长内容在 `references/`（映射表、评分手册、审计清单）。
